# Game-data candidate: release handoff

This is an operator checklist, not evidence of the live VPS, Telegram configuration, installed devices, or live game behavior. The actual Mini App URL, DNS, active release SHA, secrets and mounts require production inspection by an authorized operator. The checked-in target is `https://madhouse-wiki.ru`, but the URL configured in Telegram must be verified independently.

Local migration probe: the state-store source from `218ed211` wrote an encrypted synthetic account with a pending manual checkpoint. A copy was opened by the candidate, the checkpoint survived schema migration, and a newly recorded dispatched bridge attempt survived reopening. No transport was started. The old revision has no bridge-attempt journal, so this does not prove that it can safely read or retain the candidate's unresolved journal on rollback.

1. Before release, confirm that the Mini App and all bot/menu entry points use the supported Wiki origin and that same-origin `/api/*` reaches the VPS Wiki runtime. A static or Vercel Wiki does not provide the durable stored-read runtime. Verify unauthenticated requests fail closed, and verify the authorized stored path with an explicitly authorized test account only.
2. Build Wiki and Connector from the same reviewed commit and compare each `/healthz` release marker. Select a separately built, tested bridge that advertises stop acknowledgement; an older bridge can connect, but cannot supply that proof and uncertain operations remain unresolved. Do not treat the Python relay bundle as a client installation.
3. Verify both services use the same private storage origin and storage token, the same `ACCOUNT_SESSION_KEY` and `WIKI_SESSION_KEY` respectively, and distinct keys for these purposes. Preserve account encryption and signing keys. Check the private executor and, if enabled, bridge IPC secrets match the corresponding peer but are independent of storage/session keys. Never print key values. Verify the Wiki automation volume and, when bridge is enabled, both bridge-state and separate witness mounts persist across replacement.
4. Use exactly one Wiki instance/executor; do not scale or overlap old and new workers. Retain the updater's stop-and-lease-expiry wait, health gates and independent rollback pointer. Stop the release if storage, secret agreement, bridge witness, route identity, worker lease, health or release SHA cannot be verified.
5. Back up the persistent volumes consistently while writers are stopped and keep the backup protected. Validate the candidate on a synthetic copy of the previous schema, including pending/uncertain operations and owner leases. Confirm restrictions survive restart and the original mutation is never replayed. Existing focused evidence includes `scripts/automation/state-migrations.test.mjs`, `scripts/automation/bridge-attempt-store.test.mjs`, and `tests/bridge/automation-actor-crash-recovery.test.mjs`; these do not establish compatibility with every deployed database revision.
6. **Rollback is conditional on state compatibility.** The updater's automatic old-image rollback in `vps-deployment.md` is not by itself proof that an older image understands the newer durable journal. Before enabling it for this candidate, verify the exact previous image against a synthetic copy containing the new journal/witness and unresolved attempts. If it can ignore or erase a fence, do not restart it on that state: keep game dispatch stopped, preserve all current state and investigate or roll forward. Never restore an old snapshot over a newer journal or witness merely to make the old image start. Do not switch to Vercel as a substitute for durable Wiki personal-state operations.
7. After health and compatibility checks, obtain separately authorized real-device and real-game acceptance, including actual bridge version and a safe read. Record what was tested and stop the release on any ambiguity. Do not infer a mutation outcome from reconnection, relay stop acknowledgement, timeout or a negative read. Prepare release version and changelog per `AGENTS.md` before publication.
