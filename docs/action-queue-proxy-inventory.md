# Игровые маршруты вне очереди: инвентаризация прокси

Срез контракта `public/api-docs/openapi.json` для релиза 1.4.7. Контракт получен из клиентских наблюдений и не является гарантией поведения игрового сервера. Таблица охватывает все операции с методами POST, PUT, PATCH и DELETE, допущенные документированным прокси; она не утверждает, что каждая такая операция изменяет данные.

## Общая граница для прямого обращения к прокси

- Прокси сверяет путь и метод с контрактом, требует явный заголовок разрешения мутаций и, когда указано в контракте, синтаксически корректный Bearer. Идентичность и права проверяет игра; сам прокси не создаёт подтверждённый аккаунт очереди.
- Прокси передаёт запрос upstream. У прямого вызова нет долговечного намерения, checkpoint или сверки очереди; автоматическое восстановление результата и безопасная отмена после отправки не подтверждены. Потерянный ответ не доказывает, что действие не выполнено.
- Прокси сам не повторяет запись. Поведение клиентских или внешних вызывающих сторон не установлено. Серверные исполнители могут использовать тот же игровой путь со своей защитой; наличие пути ниже не доказывает и не опровергает наличие отдельного адаптера очереди.
- `POST /api/works/open` в реализации фермы используется как чтение состояния; два маршрута `/api/auth/*` относятся к авторизации. Семантика остальных маршрутов в этой таблице не подтверждается одним лишь HTTP-методом.

Источники: `scripts/api-operations.mjs`, `api/[...path].js`, `scripts/deploy/production-api.mjs`, `scripts/automation/runtime.mjs`, `scripts/account/snapshots.mjs`, `scripts/automation/work-farm.mjs`. Очередь допускает только типы, перечисленные в `scripts/automation/service.mjs`; сопоставление каждого игрового маршрута с исполнителем и доказательством сверки ещё требует отдельной проверки.

## Установленные связи с серверными исполнителями

Эти связи относятся только к вызовам через сервер автоматизации. Прямой вызов того же пути через документированный прокси сохраняет описанные выше ограничения. Для одноразовых действий отмена до отправки проверяется через `canDispatch`; после отправки отмена не отменяет запрос и неопределённый результат остаётся на сверке. Для длительных задач карточка запуска передаёт управление соответствующему исполнителю: дальнейший прогресс и остановка принадлежат ему, а не повторному запуску карточки.

Связи выше не означают, что все действия длительных исполнителей представлены отдельными типами очереди. Результаты и неопределённость конкретных игровых запросов следует сверять по состоянию их владельцев. Маршруты вне этих связей не считаются проверенными адаптерами только на основании OpenAPI.

Начиная с версии 1.4.8 бизнес-коллектор, автобой и рейд сохраняют ограниченную историю квитанций запуска до уведомления о старте. Это позволяет сверить старое намерение после замены текущего исполнителя. Если в старых записях нет квитанции и наличие другого исполнителя не позволяет доказать, что запуск не состоялся, адаптер оставляет результат неопределённым и не запускает операцию повторно.
