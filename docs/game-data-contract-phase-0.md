На VPS actor lease и SQLite state-store защищают владение automation worker, но не координируют игровые отправки независимого процесса connector и остальных путей. In-memory `account-queue` не обеспечивает межпроцессный бюджет. Допуск будущего транспорта должен атомарно охватывать оба процесса и каждый отдельный запрос через bridge; при недоступности координатора нельзя переходить на native fetch. Нужно повторно проверить route/binding и `canDispatch` непосредственно перед физической отправкой, не удерживая слот при ожидании следующего запроса или backoff. ## 1. Термины и границы доказательства

- **Wiki request** — HTTP к нашему серверу. Например, `GET /api/automation/state` не является игровым запросом сам по себе, но его обработка сейчас может породить несколько игровых отправок.
- **Игровая отправка** — фактический HTTP к игровому origin, включая identity/auth, повтор, probe, чтение через TLS-туннель устройства и POST-чтение `/api/works/open`. Передача задания устройству и его HTTP к игре — одна игровая попытка, а не две.
- **Снимок** — серверные персональные данные, подтверждённые ответом игры. Каталог SQLite содержит публичные определения и происхождение, а не персональные снимки.
- **Текущее** ниже означает установленное по коду. **Проект** — требование следующей реализации. **Не установлено** — нужен отдельный эксперимент на fake API, проверка конфигурации или подтверждение upstream-семантики.

Карта покрывает классы инициаторов и все обнаруженные границы физической отправки, а не утверждает, что каждый маршрут OpenAPI вызывается при старте TMA. Реестр прокси строится из [OpenAPI](../public/api-docs/openapi.json) через [api-operations](../scripts/api-operations.mjs); это наблюдаемый клиентский контракт, не гарантия игры. Отдельная [инвентаризация мутаций прокси](action-queue-proxy-inventory.md) полезна как индекс, но её исторические соответствия адаптерам нужно сверять с текущим `service.mjs`.

[App](../src/app/App/App.jsx) читает Wiki inventory-snapshots при открытии inventory, а pull refresh собирает `me`, `bag`, `floors`, `stash/sets` и видимые floor info с `fresh`, `serverRefresh: live`, `afterPending`. `production-api` передаёт Snapshot-Refresh только для `/api/me`: `fresh:true` клиента для прочих секций означает обход памяти клиента, но **не гарантирует** обход серверного cache.

Уточнение ошибок: `game-outage.mjs` регистрирует обычные 5xx/transport failures и учитывает Retry-After при probe; обычный 429 не создаёт общую паузу в этой обёртке сам по себе. Отдельные queue adapters и queue cooldown обрабатывают свои 429. В `production-api` Retry-After передаётся только для числового значения при status 429; HTTP-date этим прокси не сохраняется. Это ещё одна причина учитывать raw headers до преобразований.

Клиентские повторы формируются несколькими слоями: shared GET retry, истечение TTL/focus/15-секундный refreshExpired, refresh после команды, catalogue sync и server discovery. `eventDrivenPaths` после первого `revalidate:false` сохраняется до clear сессии: это sticky-множество посещённых путей, а не учёт активных подписчиков. Обратная проблема — обычный посещённый snapshot path остаётся кандидатом periodic refresh без активного потребителя. Таймер App на 1 с проверяет локальный статус сессии; считать его автоматически игровым polling нельзя.

Не установлены: реально активные overlay/env, число реплик и legacy endpoints, выходные IP/NAT, параллельно запущенные CLI, upstream лимиты, безопасный RPS, точная полная трасса старта TMA. Это требует отдельного конфигурационного аудита/метрик; фаза 0 не открывает доступ к секретам и не разрешает live verification.

## 4. Проект контракта данных

Это внутренний серверный API. HTTP URL можно сохранить адаптерами; названия ниже не требуют нового публичного endpoint или библиотеки.

### 4.1 Общие входы и результат

```ts
type Scope = {
  accountId: VerifiedAccountId; // только из server-owned Wiki binding
  bindingVersion: number;
  routeVersion: number;
};
type ResourceKey = {
  name: RegisteredResource;
  params: CanonicalResourceParams; // id, cursor, locale, workId и т. п.
  schemaVersion: number;
};
type Freshness = {
  maxAgeMs: number; // политика ресурса, не произвольный клиентский TTL
  minInvalidationVersion: number;
  afterBarrier?: MutationBarrier;
};
type DataResult<T> = {
  presence: "unknown" | "present";
  value?: T; // [] и разрешённый ресурсом null — present, не unknown
  freshness: "fresh" | "stale" | "unknown";
  gameConfirmedAt: number | null;
  storedAt: number | null;
  servedAt: number;
  dataVersion: number;
  invalidationVersion: number;
  confirmedInvalidationVersion: number | null;
  bindingVersion: number;
  routeVersion: number;
  refresh: {
    state: "idle" | "queued" | "running" | "waiting" | "failed";
    requestId?: string;
    reason?: ErrorCode;
    retryAt?: number;
  };
  source: "stored" | "game";
};
```

`accountId` не берётся из JWT claims, URL playerId или тела команды. Wiki principal допускается к сохранённым данным через ранее проверенную server binding; game credential — отдельная способность выполнить сеть. Истёкший игровой token/отключённый мост не должны сами требовать game login для чтения уже разрешённого сохранённого. Отзыв Wiki-сессии или разрешения binding прекращает доступ. До реализации нужно явно определить правила локального доступа при смене/удалении привязки; possession старого game token не даёт доступ к новой привязке.

Resource registry определяет схему, параметры, полноту, допустимость null, замену/merge, TTL по use case, зависимости мутаций и поддерживаемые reconciliation evidence. Ошибка парсинга, partial response и отсутствие снимка не превращаются в пустой ресурс. Составная проекция возвращает metadata по каждой секции; одна новая секция не омолаживает остальные.

### 4.3 Метаданные, поздние ответы и барьер мутации

1. Перед отправкой чтения фиксируются scope, resource schema, invalidationVersion, dispatch sequence и текущий mutation barrier. `gameConfirmedAt` означает время получения и проверки именно этого игрового ответа сервером; это не timestamp самого игрового состояния, если upstream его не предоставил. `servedAt` и `storedAt` не заменяют его.
2. Мутация получает durable operationId/checkpoint **до** отправки. На входе в конфликтующую мутацию повышается invalidationVersion затрагиваемых ресурсов и создаётся барьер. Это защищает также окно «мутация отправлена, результат неизвестен»; нельзя ждать только successful response.
3. Ответ чтения коммитится атомарным compare-and-set только при совпадении account, bindingVersion, routeVersion, schema, invalidationVersion и допустимого dispatch sequence. Если мутация или перепривязка произошла после старта чтения, старый ответ не заменяет новое значение и не очищает dirty. Повторное чтение accounts Map после await защищает соседние секции, но само по себе не выполняет этот CAS.
4. После подтверждённой мутации доверенные поля её ответа применяются по контракту ресурса; остальные связанные секции остаются stale. Разрешённое post-mutation чтение должно физически начаться после нужного барьера/подтверждения и подтвердить актуальную invalidationVersion. При uncertain действии conflict set остаётся заблокированным до reconciliation.
5. Ответ из Wiki cache, даже HTTP 200 только что полученный, не повышает gameConfirmedAt. TTL считается от gameConfirmedAt; fresh требует также совпадения версии инвалидизации/привязки/маршрута и разрешённой полноты данных. Повторное сохранение stale не делает его fresh.
6. Смена account/binding сразу отделяет client/server cache keys и pending waiters; поздний ответ предыдущего scope не публикуется в новую сессию. Route fencing остаётся в транспортном слое; успешное завершение route lease ещё не разрешает data commit после смены scope.
7. Полный snapshot, частичный patch и отсутствие поля — разные формы. Null очищает значение только если это явно допускает schema ресурса. Текущий общий merge (с отдельным исключением activeBossBattle=null) нельзя глобально менять без ресурсных правил и fixtures.

### 4.4 Совместимость чтений и спрос

Ключ физического запроса включает verified account, binding/route version, canonical resource+params/body, schema и consistency domain. `POST /api/works/open` классифицируется как зарегистрированное read, а не произвольно как mutation по HTTP-методу. Query/cursor и workId не теряются при нормализации.

Присоединение разрешено, только если уже начатый запрос гарантирует **не слабее** требования нового: минимальное время начала/барьер, invalidation version, максимальный возраст и полноту. Strict/action consumer не присоединяется к cache/stale display promise. Одинаковые требования coalesce; более сильное чтение может удовлетворить слабого потребителя, но fallback применяется отдельно к каждому потребителю. Если требования несовместимы, новый запрос ожидает барьер и повторно проверяет необходимость перед dispatch. Dedup не обязан означать вечное кеширование результата ошибки.

UI demand имеет lifecycle acquire/release; automation demand живёт в durable настройке/операции. Посещение экрана не создаёт бессрочный фоновый спрос. Dirty лишь меняет состояние; само по себе не запускает веер refresh. Priority назначается по причине, но не обходит budget, route guard, conflict barrier или cooldown. Существующие значения 1100 мс/TTL — наблюдаемые настройки, не доказанный безопасный RPS игры.

Приоритетные reconciliation/stop не отменяют ограничения; stop сначала сохраняет локальный запрет новых действий, dispatched операция остаётся видимой.

| D7  | После await section записывается с updatedAt now без CAS инвалидизации                                                                        | Фаза 3: transactional invalidation/commit и action barrier; контракт проектируется до подключения новых readers | Отложенный старый GET после мутации/смены account не меняет данные/dirty/freshness                                                    |
| D8  | Bridge profile хранится отдельно, прочие bridge reads не используют общий section store; bridge profile saved path не эквивалентен direct TTL | Фаза 3: единый data service перед двумя транспортами; route guards сохраняются                                  | Одинаковые presence/freshness/ошибки при direct и bridge; выключенный мост позволяет readStored, не прямой fallback                   |
| D9  | Successful mutation ставит dirty всем секциям; inventoryDirty уточняет лишь часть; общий merge игнорирует многие null                         | Фаза 3: таблица эффектов/ресурсные adapters по подтверждённым schemas                                           | Fake mutation инвалидирует нужное; null очистка тестируется отдельно по ресурсу; dirty не запускает сеть                              |
| D10 | Клиентская tail тормозит saved/state/stop; sticky eventDrivenPaths и несколько refresh инициаторов                                            | Фаза 4 после серверных гарантий: один Wiki state flow и lifecycle demand; убрать игровые политики из хуков      | Два компонента делят данные, unmount не отменяет другого; закрытый экран не поддерживает лишний game refresh                          |
| D11 | Stale aggregation/HTTP без всех metadata могут скрыть игровой возраст; клиент без Section-Updated использует now+TTL                          | Фазы 1/3: metadata envelope в saved endpoints и производных проекциях; фаза 4: честное применение на клиенте    | Дважды полученный stale имеет прежний gameConfirmedAt; составные данные не омолаживаются целиком                                      |
| D12 | Общий лимит и безопасные интервалы не установлены; process-local ingress limiter выглядит похожим на game limiter                             | Фаза 5: метрики на общем dispatcher, отдельный сценарный budget                                                 | Каждый game attempt имеет source/reason/account pseudonym/route/queue wait/cache outcome/attempt; нет tokens/initData/payload в логах |

Порядок внедрения: **1 — saved/session/pure state; 2 — общий dispatcher; 3 — единый data service direct+bridge с согласованностью; 4 — упрощение клиента; 5 — измерения и настройка.** Минимальная трассировка counters нужна уже при фазе 2 для доказательства охвата, подбор частот — только после сценарных измерений. Redux, TanStack Query, SSE и микросервисы не являются задачами этих фаз и не нужны для их приёмки.

### 6.1 Обязательная приёмка на fake API

1. **Ноль сети:** загрузить ранее проверенную binding и snapshots, рестартовать runtime; readStored/state при game fetch, который падает при любом вызове, возвращают данные. Missing даёт unknown; пустой подтверждённый список остаётся present. Неизвестная binding возвращает локальную ошибку без `/api/me`.
2. **Независимая доступность:** game outage, expired game token и offline bridge не мешают разрешённому Wiki saved read/stop receipt; отозванная Wiki-сессия доступа не получает. Restore не ждёт gameLogin. Уже dispatched pending action не исчезает при stop.
3. **Совместимость:** N равных читателей → одна физическая попытка; отмена первого оставляет второго; после отмены всех UI waiters unsent refresh снимается, automation demand остаётся. Cache/display promise не удовлетворяет strict/action/barrier read.
4. **Гонки:** задержать GET, отправить и подтвердить fake mutation, завершить старый GET; CAS запрещает его публикацию/очистку invalidation. Повторить со сменой account, token binding и route epoch, включая поздний bridge profile. Межсекционные чтения не затирают друг друга.
5. **Ошибка и возраст:** fake 429 с Retry-After одновременно из UI, automation, catalogue и connector вызывает общую паузу нужной области; диспетчер видит 429 до stale fallback. Stale хранит исходный gameConfirmedAt; invalid/partial response не заменяет complete snapshot; 401 и forbidden не превращаются в empty success.
6. **Durability:** fake POST выполнен, ответ потерян, сервер перезапущен. Ровно одна mutation dispatch, дальше только разрешённые evidence reads. Неполная/неоднозначная evidence → stillUnknown; отмена, смена маршрута и повтор commandId не создают второй POST. Retry возможен только после доказанного not-dispatched/not-applied или документированной идемпотентности конкретной операции.
7. **Охват процессов:** два fake процесса/owners, один общий budget и route fence; истечение/перехват lease не разрешает старому owner новые dispatch или commit. При падении coordinator система ждёт/отказывает, а не уходит native fetch. CLI и legacy route либо явно подключены, либо выключены/отдельно обозначены.
8. **Спрос и справедливость:** поток боевых действий не голодает display/reconcile бесконечно; очередь ограничена, cancel проверяется перед dispatch; отсутствие UI не останавливает включённую automation. Мутация инвалидирует без fan-out, refresh выбирает только востребованное.

Числовой request budget сценариев фиксируется по fake трассе после инвентаризации конкретного сценария и текущего состояния cache, а не выдумывается как «один запрос на открытие». Отдельно считать Wiki HTTP, cache hit, enqueued refresh и physical game attempts. Production измерения/live game testing требуют отдельного разрешения и runtime gate; этот документ их не разрешает.

### 6.2 Независимые зоны для будущей параллельной реализации
