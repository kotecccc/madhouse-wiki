# Лечение и приглашения в боях с боссами

План для Madhouse Wiki от 25 октября 2026 года. База исследования — выпущенный коммит `987d7ac`, действующие серверные автоматизации и публичный клиент игры. Ниже сохранён исходный план. В принятой реализации пользователь подтвердил `damageMax` из API как порог лечения без ручной таблицы; временные затруднения сохраняют включённый автобой и рейд в ожидании. Актуальное поведение описано в `docs/automation-state.md`.

Помощник должен вести автобой и рейд в обычном игровом темпе: лечить до опасного удара, покупать аптечки только в разрешённых пределах и приглашать друзей, когда это не создаёт явного риска недобрать норму урона. Защита от смертельной атаки действует всегда и не имеет переключателя. При отсутствии безопасного действия помощник останавливает действия с понятной причиной.

## Блок лечения

В окне босса рядом с настройками автобоя размещается самостоятельный `BaseCard` «Лечение». Внутри — общий переключатель автолечения, две строки аптечек и компактный раздел автопокупки. Ручное применение и покупку сохранить как дополнительные действия в этом же блоке.

| Элемент                | Поведение                                                                                                |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| Автолечение            | Явное включение. Если выключено, помощник всё равно не отправляет заведомо опасную атаку                 |
| Малая аптечка · 10%    | Разрешение применения, числовой лимит на бой, запас и расход `2 / 5`                                     |
| Большая аптечка · 100% | Отдельное разрешение, отдельный лимит, запас и расход                                                    |
| Докупать при нехватке  | Отдельное явное разрешение; само включение автобоя не разрешает покупки                                  |
| Валюта                 | Задаётся отдельно для каждого разрешённого к покупке типа; без автоматического перехода на другую валюту |
| Бюджет запуска         | Жёсткий предел расходов по каждой выбранной валюте на весь запуск, вместе с остатком бюджета             |
| Состояние              | «Лечимся», «Покупаем 1 аптечку», «Лимит исчерпан», «Безопасный удар невозможен»                          |

Лимит на бой означает число **применений**, включая вручную отправленные через помощника. Ручная покупка не увеличивает лимит применения. Для покупок отдельно считать количество и сумму; не покупать больше, чем осталось разрешённых применений. Покупка — по одной штуке по необходимости, существующий запас используется первым. При сериях одного ограничения на бой недостаточно: бюджет запуска не даёт потратить кошелёк за много боёв.

Начальные настройки новой функции: автолечение и автопокупка выключены, лимиты и бюджет равны нулю. Пользователь один раз задаёт и сохраняет профиль лечения для выбранного босса; он одинаков для автобоя и рейда, а при старте копируется в настройки запуска. Это не разрешение тратить валюту на других боссов. Сохранённый лимит одного боя не означает бесконечный бюджет серии.

Во время запуска разрешены немедленное выключение лечения/покупок и уменьшение лимитов. Новая конфигурация повторно проверяется перед каждым POST; уже отправленный запрос нельзя отменить. Увеличение расходов требует явного сохранения пользователем. Значение ниже уже потраченного останавливает новые расходы, не переписывает историю.

Компоненты: существующие `BaseCard`, `CardTitle`, `CardDescription`, `Button` с доступным состоянием переключения, `NumberStepper`, `SelectField`, `Pill`, `ProgressBar`. Отдельный новый Switch или визуальный вариант не нужен. Feature CSS содержит только раскладку с существующими токенами. На узком экране строки становятся последовательными блоками без уменьшения шрифта и изображений. Состояние не передаётся одним цветом.

## Постоянная защита от смерти

Перед **каждой** автоматической атакой исполнитель получает решение: атаковать, лечить, купить, ждать или остановиться. Приоритет: остановка и неопределённость → актуальность боя → выживание → разрешённое лечение/покупка → готовая атака → приглашение.

Обозначим текущее здоровье игрока `H`, подтверждённую верхнюю границу следующего ответного урона `U`. Атаковать разрешено только при `H > U`: равенство тоже опасно. Не рассчитывать на крит игрока или на то, что босс умрёт раньше ответного удара. Стратегия намеренной смерти и последующего полного лечения исключена.

`damageMax` из свежих данных босса — кандидат для базовой границы, но сначала нужно установить, включает ли он криты, модификаторы и реальный ответный удар по этому игроку. Наблюдённый максимум нескольких ударов не доказывает верхнюю границу. Произвольный запас 20% или предполагаемый множитель критов не превращает оценку в гарантию. При неизвестной границе показывать причину и не отправлять автоматическую атаку; для первого удара нельзя требовать «сначала получить удар и обучиться».

Если есть временное снижение входящего урона, учитывать его только при подтверждённой длительности и остатке действия. Консервативно не полагаться на бонус, который закончится следующим ходом. Новую автоматику боевого воя этот объём работ не включает.

Выбор лечения:

1. Построить разрешённые варианты с учётом остатка лимита, запаса, цены, бюджета и КД.
2. Выбрать малую, если одного подтверждённого применения достаточно для `H_after > U`.
3. Если нет — выбрать большую, если она делает следующий удар безопасным. Несколько малых допустимы лишь при подтверждённой механике применения и конечном плане, который укладывается в лимиты и время; после каждой заново проверить состояние.
4. При необходимости купить одну разрешённую аптечку, подтвердить запас, затем отдельным действием применить. Между действиями выдержать обычную задержку.
5. После лечения подтвердить HP, расход и новый КД. Нулевой эффект, неполный ответ или неизвестный результат останавливают действия; бесконечной цепочки аптечек быть не должно.

Если даже полное здоровье не превышает `U`, лечение не решит проблему: не покупать и не тратить аптечки. При полном HP, исчерпанном лимите, нулевом запасе без автопокупки или нехватке бюджета — остановить авто с точной причиной. Остановка не означает surrender и не создаёт фиктивное поражение. Рейд не должен после такой остановки молча включить атаки снова.

## Норма урона и приглашения

Над журналом боя показывать `Норма урона: M / Q`, полосу прогресса, `Осталось R` и состояние допуска к награде, если его смысл подтверждён. `Q = dropDamageRequired`, `M = myDamage`, `R = max(0, Q - M)`. Отсутствующее поле — неизвестное значение, а не ноль. Явный нулевой порог обрабатывается отдельно. Личные значения остаются только в приватном состоянии аккаунта.

Норма может меняться: каждое новое подтверждённое `Q` пересчитывает остаток и решение о приглашениях. Не делать достижение нормы необратимым локальным флагом. При частичном ответе сохранять прежнее значение вместе с признаком свежести, не выдавать его за обновлённое. Различать уровень допуска к наградам, выполнение нормы и фактический дроп: достижение нормы не гарантирует конкретный предмет. Семантику `myRewardEligible` нужно сверить с текущим сервером, не объявлять его автоматически эквивалентом выполнения нормы.

### Оценка времени

Для прогноза использовать только данные этого боя и собственный подтверждённый урон; прогноз не является гарантией.

- `d_low` — консервативная оценка собственного урона за ход без расчёта на крит.
- `n = ceil(R / d_low)` — оценка оставшихся ударов. При недостатке данных `n` неизвестно.
- `T_need` — время до ближайшего хода плюс интервалы оставшихся ударов, обязательные паузы, лечение и возможная покупка. Планировщик считает по верхним границам выбранных задержек и сетевому запасу, а не только по среднему DPS.
- `v_others` — оценка темпа других участников по нескольким последовательным снимкам. При полном журнале/счётчиках отделять свой урон от общего. При стабильном составе оценивать приращения участников; при частичных списках, изменении состава, лечении босса или сбросе счётчиков помечать окно непригодным.
- `T_boss` — осторожная оценка оставшегося времени жизни босса с учётом суммарного темпа, включая собственный. Ноль наблюдённого урона других не означает бесконечное время; для резких всплесков использовать запас, оцениваемый по фактическому разбросу.
- Сравнивать также `T_need` с оставшимся временем боя. Уже отправленные приглашения могут привести новых игроков позже; отказ от новой рассылки не отзывает прежнюю.

Например, при норме 50 000, собственном уроне 30 000 и осторожной оценке 5 000 за удар нужно ещё четыре удара. Если до первого хода 5 секунд, следующие интервалы по 10 секунд, потребуется хотя бы 35 секунд плюс лечение и запас. При ожидаемом завершении через 20 секунд новые приглашения откладываются. Числа иллюстративные, не параметры игры.

Нельзя достоверно оценить силу ещё не пришедших друзей. Поэтому неизвестные данные означают «сначала набрать норму», а не разрешение массовой рассылки. Первая версия может использовать это простое правило всегда; прогноз стоит подключить для более ранних приглашений только после проверки его консервативности на сценариях. Не предполагать, что будущий участник обязательно снизит `Q` и тем самым спасёт ситуацию.

### Решение о рассылке

| Состояние                                                                  | Решение                                                                                                                                              |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Норма достигнута по свежим данным                                          | Приглашать, если бой активен, есть места и сервер разрешает                                                                                          |
| Норма ещё не достигнута, хватает времени и данных для осторожного прогноза | Можно пригласить; сразу после изменения состава пересчитать                                                                                          |
| Босс заканчивается, `T_need` сравнимо с `T_boss`, либо нужно лечиться      | Отложить приглашение; продолжать только безопасные действия в обычном темпе                                                                          |
| HP босса меньше `R`                                                        | При текущем пороге нормы уже не хватит; прекратить рассылку, показать риск. Порог ещё может измениться, поэтому не объявлять результат окончательным |
| Норма, собственный урон или прогноз неизвестны                             | Не приглашать до подтверждения нормы; не выполнять частый опрос ради расчёта                                                                         |
| Бой завершён, просрочен, заполнен, есть неизвестный POST или остановка     | Ничего не отправлять                                                                                                                                 |

Первое приглашение ставится через небольшую обычную задержку после подтверждённого входа и проходит ту же проверку нормы. Требование немедленно пригласить всех конфликтует с защитой нормы в коротком бою; в этом случае приоритет имеет собственная норма. Статус объясняет: «Приглашения отложены — набираем норму».

Следующая попытка — не раньше чем через случайные 35–45 секунд **после завершения** предыдущей и не раньше серверного срока. Сохранить выбранный момент на сервере; перезапуск не должен пересэмплировать его в более раннее время. Интервал одинаков для автобоя и рейда, без пользовательских настроек приглашений. Случайность распределяет действия во времени, не используется для обхода правил игры.

`bulk` отправляет всем доступным друзьям в сети, как текущая кнопка игры, а не всем офлайн-друзьям. Пропуски агрегировать по причинам. Никакого fallback на параллельные персональные запросы. Если участнику чужого рейда запрещено приглашать, отключить рассылку в этом бою с объяснением и продолжить разрешённые безопасные атаки. Сам факт участия не доказывает право рассылки.

При известном отказе из-за КД следующий новый цикл возможен после серверного срока и новой оценки боя. При неизвестном результате POST рассылку приостановить до сверки, не создавать новый `operationId` для немедленного повторения. Если сервер не позволяет установить результат, требуется явное возобновление пользователем. Нулевое число приглашённых также не запускает немедленный повтор.

## Серверное исполнение и расходы

Нужен один исполнитель боя поверх существующего actor. Он выбирает следующее действие, а `battle-series` и `raid-waiter` управляют переходами между боями. Приглашения не получают независимый таймер, способный конкурировать с лечением и атакой. При одинаковом сроке готовая безопасная атака важнее рассылки.

Хранить в приватном checkpoint:

- профиль лечения выбранного босса и зафиксированные настройки запуска;
- запись боя по `battleId`: подтверждённые применения каждого типа, покупки, расходы, резервы и неизвестные операции;
- `runId`, бюджет запуска и его остаток; пауза/перезагрузка не обнуляют бюджет;
- фазу `attacking`, `healing`, `buying`, `waiting_cooldown`, `paused`, причину и срок следующего действия;
- `nextInviteAt`, результат последней рассылки и серверный срок ограничений;
- ограниченное окно временных меток и агрегатов урона для прогноза, отдельно от публичного каталога.

Перед POST атомарно записать тип действия, `battleId`, `operationId`, резерв применения/бюджета и текущую версию. Подтверждённый результат переводит резерв в расход ровно один раз. Неизвестный результат сохраняет резерв и блокирует повторение. Отказ снимает резерв только при доказанном отсутствии эффекта. Наличие `operationId` и `isDuplicate` не доказывает серверную идемпотентность.

Текущая проверка лечения «запас уменьшился ИЛИ HP увеличилось» недостаточна для точного автоматического учёта при действиях из другого клиента. Для автоматики нужен ответ/receipt конкретной операции, либо однозначное согласованное подтверждение. Внешнее ручное действие может сделать расход за бой неизвестным; до сверки помощник не обещает соблюдение общего игрового лимита по всем клиентам.

Ручные действия через Wiki проходят тот же actor и лимиты. Открытие блока лечения не должно останавливать авто; ручная мутация сериализуется и требует повторного расчёта. Срочная остановка отменяет ещё не отправленные действия и запрещает переход от уже выполненной покупки к новому применению.

После рестарта сверить текущий бой, сохранить лимиты и сроки. Счётчики нового боя создаются только при подтверждённом новом `battleId`; старые записи не теряются при повторном открытии того же боя. Переключение автобой ↔ рейд не сбрасывает расход. Старые сохранённые настройки мигрируют без включения автопокупок.

## Темп и число запросов

Сохранить существующие задержки ударов и длинные паузы. Лечение и покупка тоже идут последовательно с обычной задержкой, не в одной мгновенной пачке. Не сокращать КД, не отменять паузы и не ускорять атаки ради нормы. Изменение первого мгновенного автоудара на короткую задержку — часть этой работы, поскольку пользователь просит человеческий темп всех действий.

Читать состояние при входе, использовать ответы собственных действий, свежие снимки и уже существующие события. Перед рискованной покупкой получать актуальные цену/запас; не добавлять GET перед каждым штатным ударом. Для рассылки один дополнительный GET допустим только при устаревшем состоянии и наступившем сроке. Если ответов недостаточно для оценки, отложить приглашения. Чтения объединяются, окно прогноза не требует отдельного частого polling. Ошибки игры не создают очередь, которая затем отправится залпом.

## Что проверить до включения автоматики

| Неопределённость                                | Необходимое подтверждение                                                                       | Поведение до подтверждения                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Граница ответного урона, криты, броня, усиления | Семантика `damageMax` и применимых модификаторов, подтверждённая сервером/правилами             | Не обещать «не умирать» и не атаковать автоматически при неизвестной безопасной границе |
| Лечение                                         | КД, округление 10%, ответный удар/другие эффекты применения, подтверждение конкретного списания | Не строить неподтверждённые цепочки применения                                          |
| Норма                                           | Обновление `dropDamageRequired`, понятие активного игрока, смысл признаков eligibility          | Использовать свежий серверный порог без собственной формулы                             |
| Приглашения                                     | Право рядового участника, вместимость, область КД и бюджета, причины отказа                     | Не обходить отказ и не размножать запросы                                               |
| Покупка                                         | Однозначное подтверждение эффекта и цены, поведение при гонке с другим клиентом                 | Сохранять неопределённость и не повторять                                               |
| Допустимость помощника                          | Актуальные правила автоматизации и лимиты игры                                                  | Человеческие задержки сами по себе не подтверждают разрешение автоматизации             |

Начать с имеющихся обезличенных форм ответов и публичного кода. Недостающие сведения получать из документации/ответа администрации либо отдельно согласованной проверки. Этот план не требует живых покупок, ударов или рассылок; их в исследовании не было.

## Этапы реализации

1. **Уточнение контракта и приватная проекция.** Добавить норму, свежесть, собственный допуск к награде, лимит участников и входящие удары с сохранением полей частичных ответов. Проверить источник безопасной верхней границы. Показать норму в UI без изменения игровых действий.
2. **Общий выбор действия.** Выделить чистую функцию решения и серверный исполнитель; научить серию переживать собственные фазы лечения/покупки, не путая их с ручной остановкой. Закрыть повторный запуск опасного боя рейд-ожидателем.
3. **Лечение из запаса.** Настройки двух аптечек, постоянная защита от смертельной атаки, расход по `battleId`, безопасная остановка и серверная миграция. Пока без покупок.
4. **Автопокупка.** Явные валюты и бюджеты запуска, проверка свежей цены, резервирование, подтверждение, отсутствие повторов. Интеграция ручных действий в общий учёт.
5. **Приглашения.** Один bulk, сохранённый случайный срок 35–45 секунд, серверные ограничения, сначала консервативное правило «после нормы», затем проверенный прогноз для более ранних приглашений.
6. **Завершённый UI и выпуск.** Блок лечения, прогресс нормы и причины ожидания; фиктивные сценарии, обязательные проверки и обычный release workflow. Визуальная проверка — только по отдельному явному запросу пользователя.

Основные файлы: `boss-battle-controller.js`, `boss-battle-auto.js`, `boss-battle-request.js`, `boss-battle-remote.js`, `BossMedicinePanel.jsx`, `BossBattlePanel.jsx`, `BossBattleGoalPanel.jsx`, `scripts/automation/service.mjs`, `battle-series.mjs`, `raid-waiter.mjs`. Чистую логику выживания и прогноза вынести в небольшие отдельные модули. Описания команд и миграций добавить в `docs/automation-state.md`.

## Проверка готовности

Фиктивные ответы и управляемые часы должны покрывать:

- `H = U`, неизвестный максимум, крит и окончание бонуса; полная аптечка не помогает; малая действительно выводит выше границы;
- расход последней аптечки, разные лимиты двух типов, нулевой бюджет, новая цена, неподходящая валюта, невозможность купить;
- лечение без эффекта, потерянные ответы, перезапуск между покупкой и применением, подтверждение результата дважды;
- общий учёт ручных действий Wiki, неизвестное внешнее действие, новый `battleId`, повторное открытие старого, остановка во время GET и после POST;
- изменение нормы вверх/вниз, пропущенные поля, неизвестный собственный урон, превышение нормы без гарантированного дропа;
- сильный союзник, новый участник, босс с HP меньше остатка нормы, истекающий бой и исчерпанное окно лечения;
- приглашение одновременно с готовой атакой/лечением, отсутствие мест, запрет участнику рейда, 429, `Retry-After`, пустой результат и неизвестная рассылка;
- закрытие браузера, сохранённые сроки после рестарта, потерю lease/хранилища, истечение сессии и невозможность автоматического повтора POST;
- ровно один выполняющийся игровой запрос на аккаунт и отсутствие обхода серверного КД.

После согласованного блока изменений: релевантные unit/integration/render-to-string тесты, ESLint/Prettier изменённых файлов, `npm run lint:ui` и сборка. Полный `npm run check` — перед выпуском, без дублирования уже успешных constituent checks. Telegram-карточки локально не генерировать. Браузерные и визуальные проверки не входят в разрешённую проверку этого задания.

Критерий результата: пользователь включает автобой или рейд с сохранёнными настройками лечения; сервер соблюдает ограничения применения и покупок, не отправляет известную смертельную атаку, объясняет остановку и управляет приглашениями без ускорения боя. Норму помощник стремится набрать, но не гарантирует её в бою с независимыми участниками.
