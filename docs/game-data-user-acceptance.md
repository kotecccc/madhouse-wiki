Candidate code: `d701017a8b626077519721e0c6cb536284554d52`. All accounts and game responses below are synthetic, served on loopback. No game, production account, deployed service or installed bridge was contacted. Screenshots are local, untracked files under `artifacts/game-data-acceptance/`; no credential was included in them.

- An initial manual AccessToken login on a clean fake account left profile loading because strict stored reads could not establish an unverified identity. Explicit manual login now performs a live profile read; the subsequent UI shows the profile and timestamp. Reload reads the saved profile and reports that data may be stale/incomplete. This explicit first login is a game read; strict saved reads remain local.
- With fake game `offline`, saved profile remained visible and the queue reported missing saved state rather than spinning. Fake `429` with an explicit live refresh returned a stale profile, HTTP 200 and `X-Madhouse-Game-Status: unavailable`; the raw status/cooldown path is verified in the separate bridge and scheduler tests. The manual fixture itself is not a production scheduler.
- A missing bag displayed an unavailable-effects message; after an explicit fake read saved an empty bag, that error disappeared on reload. This comparison uses the controlled fixture and is not a claim that every resource's empty representation is interchangeable.
- The opt-in `/__fake/connect` test bootstrap used the real Wiki session signing and verification code, a synthetic encrypted account and a fake account store. Wiki session and saved automation state were restored without game fetch: the fake counter was zero; after explicitly seeding a profile it was one, and remained one after reopening the saved screen. This is a test connector, not an interactive Telegram Connector or production identity proof.
- A synthetic game token expired after five seconds while the test Wiki session remained valid. The saved profile stayed visible and the profile menu showed `Переподключить игру`. Logout removed the opt-in; a second synthetic token loaded `Fake player B` without displaying the first profile. Late responses across account switches are additionally covered by `tests/session-api.test.js`; an artificially delayed response was not visually exercised in this run.
- A supported `subscription.start` was issued through the normal automation command API using the synthetic game token. The UI showed `Подписка на рейды Выполняется`; it remained after reload and also after restarting the fake stand with the same state directory. Separately, on a fresh `ui-raid` fixture the detected raid card exposed `Подписаться`; clicking it added the subscription to the server queue and reload showed it running. Clicking stop while a fake read was held returned an intermediate `Завершаем рейд` state in 328 ms; that observation is an acknowledgement, not proof of an immediate remote cancellation. While a separate fake game read was held, opening the queue including the accessibility snapshot took 245 ms and clicking stop through UI until the empty state appeared took 194 ms, on this local machine and one run. This is not a latency guarantee and the held request is not the production executor's full paced queue. The UI accepted stop; the held game request remained independently in flight. Actual pacing and dispatch safety have separate automated coverage.
- A synthetic durable uncertain attempt was placed in the test store, followed by a restart. Queue UI reported the unknown outcome and unavailable automatic check, stated that its type could not be recovered, and did not offer replay. The test stand does not run a real bridge gate; transport stop, crash and permit checks are separately tested with the real relay and fake game. A single linked known queue action is identified where the server has sufficient journal data. The UI does not claim that stopping a relay cancelled an already received game action.

The synthetic fixture covers this subscription path, not every automation or game action. A signed, installable production bridge source revision and release version still need to be established.
