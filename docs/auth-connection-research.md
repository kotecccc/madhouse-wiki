# Подключение игрового аккаунта: проверка 20 октября 2026

## Требуемый результат

Вход в игровой аккаунт из Wiki автоматически или одной кнопкой, без копирования
JWT/initData. Поддерживаются Telegram на телефоне, Telegram Desktop и Telegram Web.
Установка расширений, мостов и другого дополнительного ПО исключена пользователем.

Рабочий вход из Wiki пока **не реализован**. Доказаны обмен свежего игрового
initData и работа production-прокси с полученным JWT. Отдельно доказан отказ
игрового endpoint при передаче свежего initData нашего Wiki-бота.

## Воспроизводимые наблюдения

Один и тот же запрос выполнялся из браузерного контекста официального игрового
origin `https://cargohustle.online`:

```js
fetch("/api/auth/telegram", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ initData }),
  credentials: "omit",
});
```

В auth-запросе отсутствовал Authorization; cookies не отправлялись. После
успешного обмена выполнялся только read-only `GET /api/me` с новым accessToken.

использует последующий строгий тест.

### Как получали новый запуск

В существующем Telegram Web целевого пользователя открывали официальный чат и
кнопку «Играть». Из реально появившегося iframe читали launch URL только в памяти,
поле `tgWebAppData` извлекали одним `URLSearchParams.get`, без повторного decode.
Для контрольного обмена использовали именно эту строку.

Telegram может повторно показать уже открытый игровой iframe со старым
auth_date. Повторное нажатие «Играть» не гарантирует новую строку. Перед одним из
успешных тестов старый Mini App полностью закрыли и подтвердили отсутствие
iframe, затем открыли заново. Старые 401 не доказывают невозможность обмена;
точный допустимый возраст initData и причина каждого старого отказа неизвестны.

### Последующие проверки: однократное использование и серверный обмен

В 20:08 UTC один свежий payload последовательно проверили без старого Bearer:
из браузера игры — 200, через локальный сервер — 401, повторно из браузера — 401.
Все три запроса выполнились при возрасте initData 0 секунд.

Чтобы исключить конкурирующий auth-запрос официального iframe, в отдельной
диагностической вкладке временно блокировали загрузку `app.*.js` игры через
DevTools Network. В 2026-10-20 20:09:13.441 UTC полученный запуск возрастом
0 секунд **сначала** обменяли через локальный Node-сервер:

- `/api/auth/telegram`: 200, новый JWT присутствует; старый Bearer и cookies
  отсутствовали, redirects запрещены;
- `/api/me` с новым JWT через тот же сервер: 200, строгая проверка JSON object;
- повторный обмен того же initData в браузере игры: 401.

Это свидетельство однократного использования проверенных initData. Полная
серверная политика replay/freshness неизвестна. Временная блокировка скрипта
после проверки снята, диагностическая вкладка закрыта. Такое вмешательство
использовалось только для диагностики; в продуктовый flow оно не входит.

## Работающий бот-компаньон

Свежие ответы `@MadhousePremiumBot` на `/bridge` и `/connect` прочитаны в
пользовательском аккаунте. `/connect` затем отменён командой `/cancel`.

- `/bridge` описывает отдельный мост на устройстве пользователя, через интернет
  которого бот отправляет запросы игре.
- `/connect` просит вручную отправить игровой JWT, `cargo_auth_session`, initData
  или launch URL. Для браузера предлагается закладка-помощник.
- Бот предупреждает о полном доступе к игровому аккаунту по переданному JWT и
  коротком сроке приёма initData. Точные сроки в его инструкции являются
  заявлениями компаньона, а не серверной спецификацией игры.

Этот flow не удовлетворяет требованию Wiki об отсутствии дополнительного ПО и
ручного переноса секретов. JWT компаньону не передавали, мост не устанавливали,
его настройки и игровые автоматизации не изменяли.

## Текущий клиент и граница контракта

Публичный HTML игры повторно проверен: он загружает `app.b3a2797399.js`.
Файл: 3382907 байт, SHA-256
`b3a27973995a3548e58fd6a3a8b315ebcff60685d700425e8dff1de5039640c8`.
Он побайтно совпал с исследуемым локальным `/tmp/madhouse-client.js`.

В обнаруженном обычном flow клиент берёт `Telegram.WebApp.initData` и отправляет
JSON `{ initData }` на `/api/auth/telegram`. Старый Bearer опционален в клиентском
транспорте, но для доказанного свежего обмена он не потребовался.

В этом bundle не найдены строки `returnUrl`, `redirectUri`, `callbackUrl`,
`postMessage`, `refreshToken`, `/api/auth/refresh`. Найденный `start_param`
обрабатывается для `/api/partner-campaigns/hooligans/confirm`; это не найденный
auth callback. Такой поиск не доказывает отсутствие всех непубличных возможностей
серверной стороны. Полная серверная auth-спецификация не опубликована в проекте.

## Возможности Telegram

- [Mini Apps: проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app):
  HMAC связан с токеном бота. Для проверки Ed25519 третьей стороной в строку
  проверки включается bot_id. Данные Wiki и игры не взаимозаменяемы автоматически.
- [Mini Apps JavaScript API](https://core.telegram.org/bots/webapps):
  `openTelegramLink` открывает Telegram-ссылку. Документированного возврата JWT
  или initData открытого стороннего приложения в вызывающую Mini App нет.
- [messages.requestWebView](https://core.telegram.org/method/messages.requestWebView)
  и [messages.requestMainWebView](https://core.telegram.org/method/messages.requestMainWebView)
  возвращают launch URL Telegram-клиенту и доступны только пользовательским
  сессиям. Bot API token Wiki не заменяет такую сессию.
- [Telegram Login / OIDC](https://core.telegram.org/bots/telegram-login)
  подтверждает личность для зарегистрированного приложения. Наличие Telegram
  ID token само по себе не доказывает возможность обменять его на JWT Madhouse.
- [Вход в пользовательскую Telegram-сессию](https://core.telegram.org/api/qr-login)
  — отдельный вариант, требующий явного входа и собственного
  [api_id](https://core.telegram.org/api/obtaining_api_id). Это полноценная сессия
  Telegram, а не делегирование доступа только к игре. Никакая такая сессия в
  рамках этой работы пока не создана. Пользователь разрешил исследовать этот
  вариант после объяснения полного scope Telegram-сессии.

## Локальный прототип отдельного Telegram-клиента

Изолированный прототип подготовлен вне Git checkout:
`/Users/mac/.config/madhouse-wiki/auth-spike`, локальный адрес
`http://127.0.0.1:4198/`. Он не опубликован и не изменяет production Wiki.

- React + `@mtcute/web` 0.32.5; сборка Vite прошла.
- Реальный неавторизованный `help.getConfig` через браузерный WebSocket успешно
  вернул Telegram config. Использован публичный тестовый API ID из официального
  исходного кода Telegram Desktop, разрешённый только для тестов. Пользовательский
  вход с ним в прототипе запрещён. В production он не переносится.
- Для отдельной сессии предусмотрены номер/код/2FA и QR. Дальнейший код использует
  `openWebview` для `imadhouse_bot`, проверяет точный origin launch URL и сразу
  обменивает initData через фиксированный локальный auth-прокси.
- Telegram-сессия предназначена для IndexedDB самого браузера, без экспорта
  строки сессии или отправки её серверу. Игровой JWT в прототипе хранится только
  в памяти. Серверный proof API возвращает только JWT и безопасные метаданные;
  профиль в proof UI не выводится.
- Предусмотрены повторный запрос нового игрового входа и `auth.logOut` для отзыва
  отдельной Telegram-сессии. Вход, восстановление сессии, повторная выдача JWT и
  отзыв **ещё не проверены** на пользовательской сессии или всех трёх платформах.
- Нужны собственные `api_id`/`api_hash`; страница `my.telegram.org/apps` сейчас
  требует пользовательского входа. Секреты других проектов не извлекались.

При последующей интеграции важно явно объяснить: API Hash браузерного клиента
будет доступен его пользователям, хотя в Git его хранить не следует. Это
параметры приложения; они не заменяют Telegram-сессию пользователя. Исходная
полная Telegram-сессия всё равно имеет технически широкий доступ к аккаунту,
даже если код Wiki вызывает только необходимые методы и отключает updates.

## Что требуется для завершения

В проверенном публичном контракте отсутствует путь, который выдаёт Wiki новый
игровой JWT по её собственной Telegram-идентификации или возвращает Wiki
результат входа, выполненного в официальной игре. Это текущий конкретный пробел
интеграции, а не доказательство универсальной невозможности.

Подходящий контракт со стороны игры мог бы принимать Telegram-подпись Wiki для
доверенного bot_id либо выдавать одноразовый код после входа в официальную игру
с обменом на стороне Wiki. Потребуются согласованный scope, срок действия,
повторный вход и отзыв. Такие endpoint/callback нельзя выдумать на стороне Wiki.

Отдельный пользовательский Telegram-клиент внутри Wiki требует собственного
API-приложения, подтверждённого входа и проверки на всех трёх платформах.
Существующую сессию другого аккаунта из Frontend Punks для этого не использовали.

До выбора и доказательства такого пути интерфейс автоматического входа не
добавлен. Каталог SQLite не менялся; auth-ответы и персональный прогресс в него
не записывались. Git index, commit, push и deployment не выполнялись этим чатом.
