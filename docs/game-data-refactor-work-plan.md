# Game data refactor: рабочий план

Цель: воспроизводимое локальное fake-окружение для проверки восстановления, данных и клиентского поведения. Production, игровые запросы и визуальные проверки не входят в текущий scope.

## Текущее состояние

- Фаза 1 и общий VPS executor реализованы; исходный контракт и ограничения: `game-data-contract-phase-0.md`.
- Журнал bridge-попыток durable, но подтверждённый recovery permit и адресное разрешение возможной отправки отсутствуют. При неизвестном результате повтор мутации запрещён. Не считать закрытие WebSocket доказательством отсутствия поздней обработки.
- Глобальная блокировка неподтверждённой идентичности и несовпадения хранения direct/bridge остаются открытыми.
- На старте goal локальный `main` чист; upstream `d4d5bb25` интегрирован. Соседний bridge checkout содержит чужие изменения и не используется для записи.
- Локальный API автоматизации показывает адресный `recovery` (`clear`, `unresolved` или `unavailable`) без credentials и без игровых запросов; для незавершённых попыток честно сообщает, что автоматическая сверка пока не подключена. Проверка — `tests/automation-service.test.mjs`.
- Даже когда транспортный журнал уже завершён, actor с `reconciling` не отображается как `clear`; флаг автоматической сверки отражает доступность server heartbeat, а не подтверждённый результат.
- Завершившаяся локальная bridge-попытка больше не занимает обычный in-flight слот при неопределённом результате. Ограничение аккаунта и устройства остаётся отдельным fence: durable для записанных мутаций, временным для прочих неизвестных транспортных ошибок. Это ещё не разрешает recovery и не доказывает закрытие удалённых буферов; проверка — `scripts/game/direct-scheduler.test.mjs`.
- Stop/cancel принимаются по действующей Wiki-сессии через сохранённого actor; прочие команды требуют игровую авторизацию. `queue.cancel` на сервере больше не вызывает игровую идентификацию. Клиентская очередь stop и strict saved read отделена от игровых запросов и pacing. Проверки — `tests/wiki-local-stop.test.mjs`, `tests/automation-service.test.mjs`, `tests/session-api.test.js`.
- Следующий обычный клиентский запрос восстанавливает revalidation ресурса после разового `revalidate:false`; повторные event-driven вызовы сохраняют прежнее отсутствие polling. Проверка — `tests/session-api.test.js`.
- Аудит снимков выявил общий рекурсивный merge без контракта полноты. Расширение этого merge на bridge отклонено: оно могло бы сохранить удалённые поля и выдать частичные данные за свежий полный снимок.

## Результаты и проверка

1. Восстановление: связать checkpoint и попытку, ограничить серверный permit, отдельно учитывать транспорт и результат; unresolved должен сохраняться и быть доступен локальному API. Проверить crash с работающим relay и fake game.
2. Данные: согласовать сохранённые ресурсы direct/bridge, freshness, invalidation и защиту от устаревших ответов; доказать нулевой игровой трафик strict readStored.
3. Клиент: устранить искусственное ожидание локальных команд, дублирование polling и устаревшие ответы, показывать состояние и возраст сохранённых данных.
4. Приёмка: fake transport и restart-сценарии, `npm run check`, connector build, профильные тесты и воспроизводимые инструкции. Визуальное тестирование и реальные запросы запрещены без отдельного разрешения.

## Следующий шаг

Проверить точные границы допуска recovery и сохранения результата вместе с действующим actor checkpoint. Не разрешать мутации или снимать transport fence на основании таймаута, reconnect либо отрицательного чтения.
