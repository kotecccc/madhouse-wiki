# Game data refactor: рабочий план

Цель: воспроизводимое локальное fake-окружение для проверки восстановления, данных и клиентского поведения. Production, игровые запросы и визуальные проверки не входят в текущий scope.

## Текущее состояние

- Фаза 1 и общий VPS executor реализованы; исходный контракт и ограничения: `game-data-contract-phase-0.md`.
- Журнал bridge-попыток durable. Доверенный permit для read-only сверки queued `battle.attack` ограничен конкретным checkpoint и доказанной остановкой relay; исход игры и fence остаются unresolved. При неизвестном результате повтор мутации запрещён. Не считать закрытие WebSocket доказательством отсутствия поздней обработки.
- Глобальная блокировка неизвестной идентичности допускает только подтверждённый owner lease и строго заданные шаги авторизации через подписанный IPC. При отключённом публичном bridge можно включить `MADHOUSE_BRIDGE_RECOVERY_ONLY=1` на обоих VPS-сервисах: сохраняются внутренние проверки маршрута/lease и private IPC, публичные bridge HTTP/WebSocket и release не открываются. Режим требует существующие state и witness; чистое provisioning запрещено. Несовпадения хранения direct/bridge остаются открытыми.
- На старте goal локальный `main` чист; upstream `d4d5bb25` и последующий `5180fc38` интегрированы. Соседний bridge checkout содержит чужие изменения и не используется для записи.
- Локальный API автоматизации показывает адресный `recovery` (`clear`, `unresolved` или `unavailable`) без credentials и без игровых запросов. Для точно связанной остановленной попытки с работающим actor показывает возможность автоматической сверки; без доказательств или при конфликтующей попытке — недоступность. Проверка — `tests/automation-service.test.mjs`.
- Даже когда транспортный журнал уже завершён, actor с `reconciling` не отображается как `clear`; флаг автоматической сверки отражает доступность server heartbeat, а не подтверждённый результат.
- Завершившаяся локальная bridge-попытка больше не занимает обычный in-flight слот при неопределённом результате. Ограничение аккаунта и устройства остаётся отдельным fence: durable для записанных мутаций, временным для прочих неизвестных транспортных ошибок. Это ещё не разрешает recovery и не доказывает закрытие удалённых буферов; проверка — `scripts/game/direct-scheduler.test.mjs`.
- Для новых queued `battle.attack` журнал дополнительно сохраняет идентификатор операции из проверенного gate/checkpoint рядом с ID задания. Остальные и старые записи не связываются задним числом; без однозначного соответствия они остаются unresolved. Проверки — `scripts/automation/bridge-attempt-store.test.mjs`, `tests/bridge/account-service.test.mjs`.
- Crash harness останавливает дочерний Wiki transport процесс после fake POST и поднимает его заново при работающих fake HTTPS и relay; `dispatched` восстанавливается, следующий POST доходит до координатора и остаётся заблокированным. Это проверка журнала и транспорта с тестовым checkpoint, не полного actor recovery: `tests/bridge/bridge-crash-recovery-harness.test.mjs`.
- В отдельной чистой копии bridge `/Users/mac/.codex/worktrees/bridge-recovery-ack/madhouse-wiki-bridge` подготовлен локальный коммит `9db18ce` от `3f409d6`: capability и подтверждение остановки конкретного туннеля, 6 Python unit-тестов. Исходный грязный checkout не изменён. Подтверждение не доказывает исход игры и не отзывает байты в TCP; доставку/установку клиента не выполняли.
- Wiki проверяет challenge на той же аутентифицированной WebSocket-сессии и сохраняет отдельный CAS-факт остановки транспорта. Permit действует только в живом контексте actor, с подходящими checkpoint, binding revision и device generation; другие попытки сохраняют свои ограничения. Рост общего урона не считается уникальным доказательством потерянного удара ни на bridge, ни на direct: тот же рост мог вызвать другой клиент.
- Fake-интеграция gateway → настоящий Python relay → TLS → fake game → SQLite проверена командой `MADHOUSE_TEST_BRIDGE_AGENT=/Users/mac/.codex/worktrees/bridge-recovery-ack/madhouse-wiki-bridge/agent/bridge.py node --test tests/bridge/tls-websocket-relay.integration.test.mjs`. Проверяется остановка после полученного POST и сохранение ограничения после рестарта; это пока не полный crash-тест автоматического actor recovery. Без указанной переменной Python-сценарий пропускается.
- Интеграционный тест `tests/bridge/automation-actor-recovery.integration.test.mjs` использует настоящий actor, router, account service, gate, координатор и SQLite. После fake-потери ответа actor без UI делает разрешённую сверку после рестарта, не повторяет POST; последующий cancel и fence переживают ещё один рестарт. Факт остановки транспорта в этом тесте подставлен, а настоящий Python relay проверен отдельным тестом выше.
- `tests/bridge/automation-actor-crash-recovery.test.mjs` останавливает настоящий actor через SIGKILL после получения fake game POST, пока relay и game продолжают работать. После восстановления и истечения lease исход остаётся неизвестным, POST не повторяется, локальный cancel сохраняется. До crash подтверждение остановки получить невозможно, поэтому автоматический обход fence не разрешён.
- Owner bootstrap защищён SQLite lease и отдельным CAS-журналом auth/profile шагов, проверяемым перед физической отправкой; credential digest и владельца связывает подписанный внутренний IPC. Fake-интеграция `tests/bridge/connector-bootstrap.integration.test.mjs` подтверждает независимую авторизацию при чужом fence, отказ выдуманному lease и сохранение блокировки уже идентифицированного аккаунта. Старые lease без журнала этапов остаются закрытыми; потерянный ответ не позволяет повторить шаг.
- Stop/cancel принимаются по действующей Wiki-сессии через сохранённого actor; прочие команды требуют игровую авторизацию. `queue.cancel` на сервере больше не вызывает игровую идентификацию. Клиентская очередь stop и strict saved read отделена от игровых запросов и pacing. Проверки — `tests/wiki-local-stop.test.mjs`, `tests/automation-service.test.mjs`, `tests/session-api.test.js`.
- Следующий обычный клиентский запрос восстанавливает revalidation ресурса после разового `revalidate:false`; повторные event-driven вызовы сохраняют прежнее отсутствие polling. Проверка — `tests/session-api.test.js`.
- Локальный опрос очереди продолжает ограниченные проверки при missing/404, не превращает malformed payload в пустую очередь и не перезаписывает новые данные поздним ответом. Missing и ошибка первого чтения показываются отдельно от загрузки; последние валидные данные сохраняются при временном сбое. Fake-clock проверка — `src/features/action-queue/stored-state-polling.test.js`, UI policy — `npm run lint:ui`.
- Секция очереди показывает `unresolved`/недоступность recovery через UI Kit; полный рабочий recovery пока не заявляется. Wiki build и `npm run lint:ui` прошли на этом изменении, визуальная проверка не выполнялась.
- Промежуточная полная проверка после локальных и UI изменений: `npm run check` — 1707 тестов и Wiki build; `npm run build:connector` прошёл. Эти результаты не подтверждают будущие изменения и не являются приёмкой recovery.
- Аудит снимков выявил общий рекурсивный merge без контракта полноты. Расширение этого merge на bridge отклонено: оно могло бы сохранить удалённые поля и выдать частичные данные за свежий полный снимок.
- Для direct snapshots барьер revision и dirty записываются до мутации, в том числе при потере ответа; неизвестные эффекты консервативно инвалидируют сохранённые секции. Если merge сохранил старые поля, раздел остаётся stale с прежним временем; сырой ответ action-чтения не подменяется снимком. Для boss detail явный `activeBattle:null` принимается только при совпадении ID. Проверки — `scripts/account/snapshots.test.mjs`; единые правила bridge и устранение универсального merge ещё не завершены.

## Результаты и проверка

1. Восстановление: связать checkpoint и попытку, ограничить серверный permit, отдельно учитывать транспорт и результат; unresolved должен сохраняться и быть доступен локальному API. Проверить crash с работающим relay и fake game.
2. Данные: согласовать сохранённые ресурсы direct/bridge, freshness, invalidation и защиту от устаревших ответов; доказать нулевой игровой трафик strict readStored.
3. Клиент: устранить искусственное ожидание локальных команд, дублирование polling и устаревшие ответы, показывать состояние и возраст сохранённых данных.
4. Приёмка: fake transport и restart-сценарии, `npm run check`, connector build, профильные тесты и воспроизводимые инструкции. Визуальное тестирование и реальные запросы запрещены без отдельного разрешения.

## Следующий шаг

Доказать полный actor recovery после crash через реальный gate и транспорт, затем устранить глобальную блокировку bootstrap без обхода маршрута bridge. Старый клиент или потеря подтверждения должны оставаться unresolved. Не разрешать мутации или снимать transport fence на основании таймаута, reconnect либо отрицательного чтения. Результат остаётся неизвестным даже после подтверждённой остановки relay, пока game evidence его не разрешит.
