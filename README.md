# Madhouse Wiki

Справочник по игре на React 19 и Vite с локальной SQLite базой справочных данных. Node.js 24 или новее нужен для встроенного `node:sqlite`. Production-сборка остаётся статической: Vite читает SQL при сборке и включает публичную модель в JavaScript.

## Запуск

```sh
npm ci
npm run dev
```

Локальный адрес: http://127.0.0.1:4174/. `npm run build` собирает сайт в `dist/`, `npm run preview` показывает сборку на http://127.0.0.1:4175/.

## Архитектура

Простая компонентная структура: разделы страницы владеют своим состоянием, общий UI kit задаёт внешний вид, слой модели разрешает связи данных. Для одной страницы FSD и полный Atomic Design добавили бы лишние уровни.

```text
src/
  main.jsx             # Только монтирование React и подключение CSS
  app/App.jsx          # Композиция страницы и открытие контекстных окон
  components/
    ui/                # BaseCard, CardText, Button, Dialog, поля, иконки, изображения
    layout/            # Логотип, шапка с мобильным меню, подвал
  features/
    floors/            # Этажи, раскрываемые работёнки, требования
    bosses/            # Каталог боссов и карточки боссов отделения
    businesses/        # Карточки бизнеса, предметы, уровни улучшений
    calculator/        # Калькуляторы полного цикла и восстановления энергии
  model/               # Индексы сущностей, порядок этажей, выборки по связям
  lib/                 # Чистые расчёты и форматирование
  styles/              # Только токены и минимальные глобальные правила

local-data/madhouse.sqlite # Каноническая SQLite база (локальный файл, исключён из Git)
scripts/catalogue/     # SQL-схема, API-импорт, фильтрация и чтение базы
scripts/validate-data.mjs
tests/                # Расчёты и рендеринг всех типов контента
```

Направление зависимостей: `app → features → components/ui`, разделы читают данные через `model`; `lib` не зависит от React. Доменная карточка принадлежит своему разделу и может переиспользоваться соседним разделом. UI kit не знает об этажах, боссах и бизнесах. Глобальный store и роутер не нужны для текущего объёма.

## UI kit

- `BaseCard` поддерживает семантический тег через `as` и визуальный вариант через `variant`.
- `CardTitle` и `CardDescription` задают общие роли текста и обрезание длинных строк.
- `Button` поддерживает `primary` / `secondary`; без варианта сохраняет стили специализированного контрола. Тип по умолчанию — `button`, отправка формы требует `type="submit"`.
- `NumberField`, `SelectField` объединяют связанные подписи и поля без дополнительных DOM-обёрток.
- `MediaTile` / `ImageTile` задают общий контейнер изображения или значения.
- `Dialog` сохраняет существующий немодальный режим окон, добавляет закрытие по Escape, начальный фокус и возврат фокуса к исходному контролу.

Каждый компонент с собственным оформлением импортирует соседний `Component.css`: например, `BaseCard.jsx` → `BaseCard.css`, `Button.jsx` → `Button.css`, `FloorWorkItem.jsx` → `FloorWorkItem.css`. Там же находятся его адаптивные правила и состояния. Компоненты-обёртки, которые только переиспользуют другой UI-компонент, не создают пустые или дублирующие CSS-файлы.

Глобальными остались только `src/styles/tokens.css` (токены) и `src/styles/global.css` (сброс, фон документа, базовая типографика, accessibility и reduced motion). Они подключаются в `main.jsx` перед приложением. Общего сборного CSS для компонентов нет.

Общее оформление переиспользуется через компоненты: поверхности и варианты — `BaseCard.css`, текстовые роли — `CardText.css`, кнопки — `Button.css`, подписи полей — `FieldLabel.css`, оболочка диалога — `Dialog.css`, контейнер секции — `ContentSection.css`. Родитель задаёт раскладку, а дочерний компонент отвечает за свой внешний вид. `SelectField` оформляет собственный select; калькулятор не стилизует его через родительский селектор.

Для новой независимой карточки используйте `BaseCard`, общие роли текста и токены. Внешняя оболочка раскрываемой работёнки сохраняет собственный дизайн. Не добавляйте локальные поверхности и типографические исключения вместо общего компонента.

## Данные

Источником служит `local-data/madhouse.sqlite`. Схема, импорт и ограничения описаны в [data/README.md](data/README.md). Старые JSON-каталоги удалены. API-контракты Swagger сохранены отдельно в `public/api-docs/`.

`node scripts/build-local-catalogue.mjs` создаёт схему и выводит текущую таблицу покрытия; эта команда не заполняет каталог старыми данными. После входа Wiki сама загружает доступность этажей и запускает импорт справочных определений для открытых этажей. Доступность каждого этажа повторно проверяется игровым API. Импортёр использует разрешённые GET и отдельно разрешённый `POST /api/works/open` с `workId` и `locale: "ru"` для описаний; игровые изменения не выполняются. В production опубликованный справочник хранится в приватном Vercel Blob, потому что файловая система функций Vercel временная. В клиент передаются только allowlist-проекции справочных ответов. JWT, профиль, прогресс и флаги доступа в общий каталог не записываются.

Импорт продолжает отсутствующие запросы; успешные ответы повторно не запрашиваются, а `409` остаётся незавершённым и будет повторён при следующей авторизации. Между игровыми запросами выдерживается пауза; новые вызовы прекращаются при `401` или `429`. В `captures` хранятся только маршрут, HTTP-статус, количество отфильтрованных сущностей и время. API не предоставляет здесь глобальные уровни и цены улучшений: 14 рецептов на 74 бизнес-уровня добавлены отдельно из данных пользователя и не подтверждены API. Источник, включая заявленный итог болтов L3 (133) и сумму строк уровней (136), указан в [отчёте каталога](local-data/catalogue-report.md) и [исходных данных](local-data/sources/user-business-upgrades-2026-10-20.md). Для обновления API-определений используйте явный режим обновления, описанный в документации базы.

Для обнаружения ID используется таблица маршрутов публичного клиента, без выполнения его кода: `node scripts/catalogue/discover-client.mjs /absolute/path/to/public-client.js`. Команда сохраняет только ID, принадлежность отделу и SHA256 источника в SQL. Описания и характеристики всё равно загружаются из API.

Локальная разработка синхронизирует тот же справочник в `local-data/madhouse.sqlite`; production использует приватную Blob-копию. После синхронизации открытая страница применяет полученные определения сразу, без перезагрузки. Не добавляйте персональные счётчики, состояние доступа и прогресс аккаунта. Неизвестная стоимость энергии не участвует в расчёте.

## Проверки

```sh
npm run check
```

Команда проверяет ссылки и ID данных, ESLint и правила React Hooks, форматирование, тесты и production-сборку. Отдельно доступны `validate:data`, `lint`, `format:check`, `test`, `build`; `npm run format` форматирует файлы.

Тесты проверяют арифметику циклов и восстановления, обработку неизвестных значений, рендеринг всех отделений и требований, карточки боссов и SQL-модель на изолированных тестовых API-ответах. Внешние игровые изображения и Google Fonts остаются зависимыми от доступности исходных CDN.

## JWT и Swagger

Вход расположен в шапке основной Wiki. JWT сохраняется в localStorage браузера под ключом `madhouse.wiki.jwt`, отдельно от справочной SQLite. Wiki и Swagger используют общий модуль `shared/auth-session.js`; открытые вкладки синхронизируются через storage events. В интерфейсе показываются срок из `exp`, оставшееся время и истечение; просроченный JWT не отправляется. Декодирование срока не проверяет подпись — действительность определяет API. `Выйти` удаляет сохранённый токен. Токен не попадает в каталог, отчёты, исходники или логи.

Swagger показывает все документированные REST-операции и отправляет их через same-origin API-прокси. GET работает с JWT Wiki. POST, PUT, PATCH и DELETE требуют включить переключатель изменяющих запросов на странице Swagger; прокси проверяет отдельный заголовок и по умолчанию отклоняет такие запросы. Переключатель не сохраняется. Модуль авторизации поставляется и в production-сборку.

## Сессионные запросы Wiki

Профиль, статы, валюты и доступность этажей/отделений загружаются через `shared/session-api.js`: только GET, общий кэш в памяти на 3 минуты, объединение одинаковых одновременных запросов и последовательная очередь с интервалом не меньше 1100 мс между началами запросов. При смене JWT, выходе или недействительной сессии прежние ответы и незавершённые запросы сбрасываются. Навигация использует кэш; открытие профиля повторно проверяет его срок и обновляет данные только при необходимости. Перезагрузка страницы очищает этот кэш. Личные данные не записываются в SQLite.

Обычный игровой запрос `/api/floors` не запускает импорт. Авторизованный интерфейс отдельно вызывает Wiki endpoint `/api/catalogue`: GET читает безопасную публичную проекцию справочника, POST принимает только код этажа и самостоятельно перепроверяет его доступность через игровой API. В Vercel Build Output для этого endpoint выделена отдельная функция до общего прокси игровых `/api/*`.

## Приватность и обратная связь

Статистика использования включается только после согласия в интерфейсе. В приватном Vercel Blob хранятся типы действий, разделы, безопасные коды объектов, время события и HMAC-псевдоним посетителя; для согласившихся пользователей Telegram Mini App также хранятся проверенные Telegram ID и username, видимые только администратору. Посетители обычного браузера остаются под случайным псевдонимом. Срок хранения — 90 дней с ежедневной очисткой. Имя профиля, текст обращений, скриншоты, сырые Mini App credentials, JWT, игровой прогресс, IP и user-agent в аналитические записи не входят. В настройках приватности можно отключить сбор и удалить свои события вместе с Telegram ID/username.

Форма обратной связи доступна в Telegram Mini App. После проверки подписи Telegram текст и необязательный скриншот отправляются напрямую в закрытый чат администратора; Wiki не сохраняет обращение. Получатель задаётся переменной Production `WIKI_ADMIN_TELEGRAM_ID` в Vercel. Остальные параметры Telegram и приватного Blob-хранилища описаны в [настройке бота](docs/launch/wiki-bot-setup.md).
